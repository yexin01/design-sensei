# Vengeance UI agent interfaces

Read from the clone at the pinned commit; nothing was executed and nothing was fetched. Library overview: `knowledge/components/vengeance-ui.md`.

## Four layers

| Layer | Where | Audience | What it does |
|---|---|---|---|
| Repo rules | `vengeance-ui:AGENTS.md`, `vengeance-ui:CLAUDE.md` | people (and agents) editing this repo | AGENTS.md holds only a Next.js block: this Next.js version has breaking changes, read the bundled docs before coding. CLAUDE.md is one line importing AGENTS.md. The `nextjs-agent-rules` markers, and the repo's own docs listing AGENTS.md among the `create-next-app` defaults (`vengeance-ui:src/app/docs/install-nextjs/page.tsx`), suggest the file was generated by that tool rather than written for this library. Nothing in it is about the components. |
| In-repo skill | `vengeance-ui:.cursor/skills/vengeance-ui/SKILL.md` plus `install.md`, `conventions.md`, `examples.md` | contributors using Cursor | Contributor copy of the consumer skill. It links to AGENTS.md and to `public/r` and still shows the `vengenceui.com/r` install URL. There is no `.cursor/rules` directory and no `.claude` directory. |
| Consumer skill | `vengeance-ui:packages/cli/templates/skill/SKILL.md` and three sibling files | projects that run the CLI | The same four files without the repo-only references; the CLI smoke test asserts the consumer copy does not point at this repo's AGENTS.md (`vengeance-ui:packages/cli/scripts/smoke.mjs`). |
| MCP server | `vengeance-ui:packages/mcp/` | any MCP client | Searches a bundled index, returns props and usage, prints install commands, fetches registry source. |

## The skill (what it tells the agent)

- Front matter has `name` and a `description` that lists triggers: landing pages, heroes, buttons, navs, text motion, or a mention of the library or its shadcn registry.
- Workflow in five steps: clarify the UI need, `search_components` (optional category), `get_component` for props, usage and dependencies, `get_install_command`, then adapt the usage snippet and do not rewrite the component unless asked.
- Rules: prefer registry components over inventing similar ones; install with the registry `componentName`, not the docs slug; follow `"use client"`, `cn` and theme-token conventions; do not strip accessibility attributes or reduced-motion handling found in registry source; keep the skill small and never paste the whole catalog into context, use the tools instead.
- `examples.md` has three walkthroughs (CTA button, text motion headline, navbar) and ends with "do not hand-roll a shine CTA, gooey title or glass nav when a registry match exists".
- Files: `vengeance-ui:packages/cli/templates/skill/SKILL.md`, `vengeance-ui:packages/cli/templates/skill/conventions.md`, `vengeance-ui:packages/cli/templates/skill/examples.md`, `vengeance-ui:packages/cli/templates/skill/install.md`.

## The MCP server

Package `vengeanceui-mcp` 0.1.0, stdio transport, built on `@modelcontextprotocol/sdk` and `zod`; it registers tools only (no resources or prompts) (`vengeance-ui:packages/mcp/src/index.ts`, `vengeance-ui:packages/mcp/src/tools.ts`).

| Tool | Input | Returns |
|---|---|---|
| `list_categories` | none | the 9 catalog categories with counts |
| `search_components` | `query`, optional exact `category` | `name`, `slug`, `componentName`, `category`, `description`, `isNew` for each hit |
| `get_component` | `name` (slug, componentName or display name, case-insensitive) | the full entry: description, npm install string, `usageCode`, `props`, `additionalPropSections`, `manualNotes` |
| `get_install_command` | `name`, optional `packageManager` (npm, pnpm, bun, yarn) | `componentName` and the `shadcn@latest add <url>` command |
| `get_component_source` | `name` | the registry item JSON, fetched over the network with a 15 second timeout |
| `list_registry` | none | the 134 entries of `public/r/registry.json` with `type`, `dependencies`, `inCatalog` |

How it works:

- Everything except `get_component_source` reads one committed file, `vengeance-ui:packages/mcp/data/index.json` (about 230 KB, generated 2026-10-07 per its `generatedAt`), loaded once on first use and cross-checked so slug and name lookups agree (`vengeance-ui:packages/mcp/src/index-data.ts`).
- The index is built by `vengeance-ui:packages/mcp/scripts/generate-index.mjs`: it regex-parses `src/lib/components-catalog.ts`, evaluates the `COMPONENT_DOCS` object literal from `src/lib/component-docs.ts` with `new Function`, and joins both with `public/r/registry.json`. It is a build step; the index must be regenerated whenever those files change.
- Search is a case-insensitive substring test of the whole query against name, slug, componentName, category and description (`vengeance-ui:packages/mcp/src/search.ts`). "animated button" matches; "button animated" does not. No ranking, no tags.
- `get_install_command` uses the GitHub raw base from the index (`vengeance-ui:packages/mcp/src/registry.ts`). The `get_component_source` tool description says the source comes from `www.vengenceui.com`, but the code requests the same GitHub base.
- `registryDependencies` in the index is filled from the npm `dependencies` array of `registry.json`, not from shadcn registry dependencies, while `dependencies` is the install string copied from the docs data. The two disagree for some components (interactive-book lists lucide-react only in the first), so an agent should compare them with the file's imports.
- `vengeance-ui:packages/mcp/src/smoke.ts` checks alias resolution, the exact install command, a registry size of at least 100 and a live fetch of `animated-button`, so it needs network access.

## The CLI

Package `vengeanceui` 0.1.0, command `init` (default). It installs agent files only, never components (`vengeance-ui:packages/cli/README.md`).

- Targets: `cursor`, `claude`, `both` (also `all`) and `mcp`; `-y` means both plus MCP and is also the default without a TTY. Options: `--no-mcp`, `--force`, `--dry-run`, `--cwd`.
- Files written (`vengeance-ui:packages/cli/src/init.ts`, `vengeance-ui:packages/cli/src/paths.ts`): `.cursor/skills/vengeance-ui/`, `.claude/skills/vengeance-ui/`, `.cursor/mcp.json`, `.mcp.json`, and a marker-delimited block (`<!-- BEGIN:vengeance-ui -->` to `<!-- END:vengeance-ui -->`) appended to `AGENTS.md` for Cursor or `CLAUDE.md` for Claude.
- The MCP entry is `npx -y vengeanceui-mcp` under the key `vengeance-ui`. Existing servers in the file are preserved; a different existing `vengeance-ui` entry is skipped unless `--force` (`vengeance-ui:packages/cli/src/write-mcp.ts`).
- Re-runs report `unchanged`; edited skill files are `skipped` unless `--force`; an existing instruction block that differs is skipped unless `--force`, which replaces it in place, and a BEGIN marker without its END marker is an error (`vengeance-ui:packages/cli/src/write-skill.ts`, `vengeance-ui:packages/cli/src/write-instructions.ts`).
- The instruction block is short: prefer registry components, use the skill and three named tools, install with the shadcn command (`vengeance-ui:packages/cli/templates/instructions.md`).
- The smoke test covers idempotency, target isolation, config merging, conflict skipping, dry run, force and appending to an existing file (`vengeance-ui:packages/cli/scripts/smoke.mjs`).

## Verified gaps

- Two install hosts appear across the agent files (GitHub raw in templates, MCP and `src/lib/registry.ts`; `vengenceui.com/r` in the in-repo skill).
- `search_components` and `get_component` only know the 76 catalog entries. The 133 block items are not in `registry.json`, so no tool can find or install them by name (`vengeance-ui:public/r/registry.json`).
- Six catalog entries have no JSON in `public/r`, yet `get_install_command` still returns a URL for them; the index also carries the docs dependency strings that are stale for ten components (details in `knowledge/implementation-recipes/vengeance-ui-install-and-verify-component.md`).
- The skill promises to keep accessibility and reduced-motion handling "present in registry source", but only 7 of 76 catalog components have any (`knowledge/components/vengeance-ui.md`).
- The generated index can lag the docs data; the generator must be rerun by hand.
- Not verified: whether `vengeanceui` and `vengeanceui-mcp` are on npm, and how any MCP client behaves with these tools.

## What Design Sensei can borrow

- Keep the agent surface small and read-only: search, get, install-command. Return compact JSON and keep detail behind tools so the skill stays short.
- Resolve aliases inside the tool (slug, registry name, display name) instead of asking the agent to know the difference.
- Generate the index from the source of truth in a build step, then validate it. This repo shows the failure mode when nothing validates the join: missing payloads, stale dependency strings, blocks nobody can find. A check that every pattern has an existing file and a dependency list matching its imports closes that gap.
- Make installers idempotent and non-destructive: marker-delimited blocks, merged JSON config, skip on conflict, `--dry-run`, `--force`.
- Separate contributor rules (AGENTS.md for the repo) from consumer guidance (the skill), and strip repo-only links from the shipped copy.
- Search needs token matching, tags and synonyms; whole-query substring search is too brittle for a design catalog.
- A "never hand-roll what exists" rule saves tokens but pushes every site toward the same components. For a design-quality tool, pair reuse with an instruction to adapt typography, colour tokens and copy, and to run the checks in the install recipe after every install.
- Do not put accessibility claims in sample content that the code does not back up (the default FAQ text in `vengeance-ui:src/components/ui/faq-accordion.tsx` claims ARIA and keyboard support the component only partly has).
